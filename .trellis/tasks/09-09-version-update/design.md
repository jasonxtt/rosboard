# Design

Use internal/buildinfo for linker metadata and internal/update for fixed GitHub discovery, archive verification, atomic state, backups, and supervision. No new dependency: x/mod is unnecessary because stable major.minor.patch comparison can be implemented with strict decimal validation and length/lexical integer comparison.

The same executable supports `supervise -config ...`. systemd starts this mode; it owns a child executable and remains running while the on-disk binary is replaced. The HTTP child downloads a pinned release and atomically publishes a pending job, then requests graceful exit. The supervisor waits for process exit before backing up the entire data directory (including WAL) and config, keeps the old binary, installs via rename, and starts a probationary child. Private inherited pipes report startup readiness and authorize activation; before activation the candidate does not serve application requests or start workers. Startup validates config, all device stores/policy wiring and embedded entry/assets. After activation, require five continuous seconds of healthy HTTP responses identifying the exact child version/PID within 20 seconds; keep the recovery journal active until then. Workers may start, but typed background RouterOS writes wait for durable success so local rollback cannot leave external changes behind. A durable install journal permits recovery after supervisor/host interruption, including interrupted restore. One previous backup only, no arbitrary rollback UI.

State lives beside the executable under .rosboard-update, outside data/config. Backup destination defaults beside it for generic installs; ROSBOARD_UPDATE_BACKUP_DIR overrides it, ROSBOARD_UPDATE_DISABLED disables installs (required for the user's production until NAS backup integration is configured). Unsupported paths/symlinks and insufficient space fail closed. Official Release URLs only, bounded requests and tar parsing, exact asset match, checksums verified before executing candidate metadata command.

API GET /api/settings/update, POST .../check, POST .../install with expected version. Existing session/origin/CIDR checks apply; an API mutation RW lock prevents in-flight mutations racing installation. Active update blocks other mutations; pending restart blocks install admission synchronously before the delayed restart callback. Status reports one last attempt and persisted stages. Frontends share a typed API/hook, with UI-native card wrappers/styles and ordinary escaped release-note text. Poll status while active and reload on verified success.

Release workflow remains VERSION-triggered. Keep VERSION unchanged until approved release; candidate test builds explicitly inject the proposed version. Publish a draft only after all four builds/checksums exist, then publish it to avoid partial release discovery.
