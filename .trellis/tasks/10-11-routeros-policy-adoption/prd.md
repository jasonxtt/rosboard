# Adopt existing rosboard RouterOS policies

## Execution boundary

The user approved the plan and requested task artifacts, one work branch, and one Draft PR. STOP after that preparation. Do not implement, deploy, or mutate RouterOS until the user explicitly resumes implementation. Trellis activation represents readiness, not permission to cross this stop boundary.

## Problem

A fresh rosboard installation, or a newly added device record, cannot manage policies left on RouterOS by an earlier rosboard scope. The policy list depends on local desired state while RouterOS objects remain scoped to the previous installation/device identity.

## Goal

Adopt supported existing rosboard routing and access-control configurations using RouterOS alone, without the previous installation, SQLite database, or export. After adoption, users manage the resulting policies through existing editors and lifecycle actions.

## Confirmed user decisions

- Include both policy routing and access control.
- Adopt an entire old ownership scope, including its shared dependencies; no per-rule selection.
- Import current configuration as a snapshot: manual target lists and fixed source IPs/CIDRs. Do not reconstruct subscriptions or terminal auto-follow.
- Allow reviewed replacement of old objects with objects generated by the current rosboard instance. A short transition impact is acceptable; uninterrupted forwarding is not promised.
- Keep the implementation minimal and reuse existing policy models, previews, jobs, and editors.

## Requirements

1. Both Aurora and Compact expose a device-scoped adoption entry point.
2. Scanning lists candidate old scopes, routing/access counts, dependencies, warnings, and concrete blocking reasons. Do not invent the old installation's name from a scope hash.
3. Scan and preview do not save policies or mutate RouterOS.
4. Preview shows imported policy summaries, snapshot limitations, and exact create/disable/delete/retain operations.
5. The user confirms that the previous rosboard has stopped managing the router before applying the reviewed plan.
6. Supported configuration retains effective matching, actions, schedules, enabled states, and meaningful precedence. Changed internal IDs and names are acceptable.
7. Missing dependencies, ambiguous ownership, unrecognized effective fields, or unsafe outside references block the entire selected scope without writes.
8. Failures remain visible and can be rechecked and retried without duplicate imports or expanded cleanup authority.
9. After success, imported policies appear in existing lists and support edit, enable, disable, and delete. Unselected scopes, local policies, and manual RouterOS configuration remain intact.

## Initial compatibility boundary

Support the current canonical rbs_<scope>_<object> identity and structures expressible by the current routing/access generators. Older unscoped identities are reported as unsupported rather than adopted by prefix. Preserve legitimate external references without claiming ownership. Do not silently drop parts of a disabled or incomplete configuration that cannot be reconstructed.

## Non-goals

- Recover the user's previous local database or repair the historical device purge omission.
- Import arbitrary hand-written RouterOS configurations.
- Select individual policies out of a shared scope.
- Restore lost subscription URLs, refresh schedules, original UUIDs, or automatic terminal bindings.
- Add controller communication, distributed locking, a generic transaction framework, or a permanent old/new object mapping.

## Acceptance criteria

- With the old database discarded, a supported fixture containing both routing and access policies can be scanned, previewed, adopted, and managed from a new instance.
- The same workflow works when the installation is unchanged but the device ID is new.
- Repeated scan/apply/retry does not duplicate imported policies; normal post-adoption reconciliation has no remaining changes.
- Out-of-scope and manual objects are not modified or deleted.
- Unsupported or stale previews stop before writes and explain why.
- Injected failures and process restart retain sufficient state to recheck and retry safely.
- Aurora and Compact offer equivalent functionality.
- Production acceptance and merge remain subject to the repository's existing review and deployment gates.
